This approach associates the tenant with the authenticated user and stores it in the session, allowing you to determine the tenant context without relying on the domain. Below, I'll outline the steps to achieve this, assuming you have a working multi-tenant setup using Django's authentication system.
Steps to Switch to Session-Based Tenant Identification

2. Store Tenant in Session Upon Login
Modify your login view or authentication process to store the tenant in the user's session after successful authentication. You can do this by overriding the login view or using a custom authentication backend.
python# views.py or authentication backend
from django.contrib.auth import authenticate, login
from django.shortcuts import redirect, render

def login_view(request):
    if request.method == 'POST':
        username = request.POST['username']
        password = request.POST['password']
        user = authenticate(request, username=username, password=password)
        if user is not None:
            login(request, user)
            # Assuming user has a related tenant (via UserProfile or custom user model)
            tenant = user.userprofile.tenant  # Adjust based on your model
            request.session['tenant_id'] = tenant.id  # Store tenant ID in session
            return redirect('home')  # Redirect to home or tenant-specific page
        else:
            return render(request, 'login.html', {'error': 'Invalid credentials'})
    return render(request, 'login.html')

3. Create Middleware to Set Tenant Context
Create a custom middleware to retrieve the tenant from the session and set it as the active tenant for the request. This replaces the subdomain-based tenant resolution.
python# middleware.py
from django.http import HttpResponseForbidden
from .models import Tenant

class TenantSessionMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        if request.user.is_authenticated:
            tenant_id = request.session.get('tenant_id')
            if tenant_id:
                try:
                    tenant = Tenant.objects.get(id=tenant_id)
                    request.tenant = tenant  # Attach tenant to request
                except Tenant.DoesNotExist:
                    return HttpResponseForbidden("Invalid tenant")
            else:
                return HttpResponseForbidden("No tenant associated with user")
        else:
            request.tenant = None  # Handle unauthenticated users (optional)
        response = self.get_response(request)
        return response

4. Update Database Queries to Use Tenant
If you're using a shared database with tenant-specific data, ensure your models and queries filter by the tenant. For example, you can use a custom manager or queryset to automatically filter by the tenant attached to the request.
python# models.py
class TenantAwareModel(models.Model):
    tenant = models.ForeignKey(Tenant, on_delete=models.CASCADE)

    class Meta:
        abstract = True

class TenantManager(models.Manager):
    def get_queryset(self):
        tenant = getattr(self.request, 'tenant', None)
        if tenant:
            return super().get_queryset().filter(tenant=tenant)
        return super().get_queryset()

class YourModel(TenantAwareModel):
    name = models.CharField(max_length=100)
    objects = TenantManager()

5. Update URLs and Views
Since you're moving away from subdomains, update your URL routing to no longer rely on subdomain-based tenant resolution. For example, remove any subdomain middleware or logic that sets the tenant based on the request's HTTP_HOST.
If you previously used tenant-specific URLs (e.g., tenant1.example.com/dashboard), you can now use a single domain (e.g., example.com/dashboard) and rely on the session-based tenant context.

Additional Considerations

Security: Ensure that users can only access tenants they are associated with. Validate the tenant_id in the session against the user's tenant relationships.
Session Expiry: Handle cases where the session expires or the tenant ID is missing. You might redirect users to a tenant selection page or log them out.
Performance: If using a shared database, ensure queries are optimized with proper indexing on the tenant field.
Scalability: Session-based tenancy works well for smaller applications but may need adjustments for large-scale systems (e.g., caching tenant data).
Logout: Clear the tenant from the session on logout if necessary:
